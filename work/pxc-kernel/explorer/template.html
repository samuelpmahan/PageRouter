A kernel for Parts, Calculations and Ticks, grown one concept at a time. Every concept is in the ledger below because at least one of five contest entries hit friction without it. 01

How a concept enters

Five Sonnet agents each built a different domain on the kernel: circuits from NAND gates, fitted models with leakage audits, explanations as checked claims, tic-tac-toe with seated policies, and an agent-allocation simulation. Each round they migrated to the newest kernel, re-drew every picture, wrote each claim before looking, and reported friction. A concept entered the kernel only when friction converged, usually from two or more entries; a single request waited.

friction in five domains→convergence→Hegel against Wittgenstein→kernel change→tests, mutation-checked→claims, then pictures→independent audit

Flows found in the traces

The flow miner reads every receipt the contest pictures produce and looks for sibling calls wired together by exact provenance, where every intermediate result is consumed inside the window. A shape that recurs and is not a composition anywhere is a subflow nobody has named yet.

What the miner says

  • Entries C and D both compute column means as lin.transpose → stat.mean, independently. That is an interface two domains needed and neither named.
  • Entry C's standardizer runs stat.mean → stat.standardDeviation → vec.standardize by hand; entry A already declared that flow as the composition stat.zScores.
  • Entry E's minimax runs game.legalMoves → game.apply → game.outcome a thousand times in imperative code: a composition waiting to be declared.
  • Entry F's eleven-step tick exists twice: as a composition and as an imperative copy.

How it was checked

  • Drive ticks are excluded; a drive is already a concept.
  • Repeated identical runs count once (distinct input hashes).
  • A shape is dropped when a longer one containing it occurs as often.
  • One mined edge was confirmed against its trace: in C's run 1, call #9 stat.mean reads at [0] of #8 lin.transpose, inside #7 fitted.standardizer.fit.
07

Independent audit of the kernel's pictures

An Opus agent that had not seen the work checked all 54 kernel picture claims against the pictures, the facts files and the code. It confirmed 51 and refuted 3. The refutations were real: brackets in a crowded margin shared lanes and hid one another, decision edges shared one vertical, a long header dropped its verdict mark, and decisions carried by a cache hit pointed at unrelated boxes with the same number in the current run. All four defects are fixed in v0.6, each refuted claim is corrected, and the cache-hit case now has a regression test.

Open

The kernel draws a call tree; every domain draws something else

In round 6 each entry named where the kernel's picture of its domain and the domain's own picture disagree most. All five answers had one shape. Circuits think in timing diagrams, fitted models in functions of training rows, explanations in a claim table, the game in moves by players, the allocator in a Gantt chart. Readers of kernel pictures take the plumbing for the meaning: a routing decision read as the explanation, an integrator bottleneck invisible across sixteen tick pictures.

Hegel: the trace is the whole, and each domain picture is a moment of it, a projection that must stay answerable to the whole. Wittgenstein: the domain's picture is the use; the call tree is grammar, and nobody reads grammar for meaning. The question for v0.7: can the kernel carry a projection, a declared domain view over a trace with provenance back to its nodes, so a domain picture is checked against the trace instead of drawn beside it?
