# Why these checks exist

I treat frontend parity as observable pages and behavior. A loaded page, a unit test, and a screenshot answer different questions; none substitutes for the others. Production authentication, payments, mail, CAPTCHA and backend writes are excluded from this local frontend.

| Check | What I exercise | Why it matters |
|---|---|---|
| Public controller and independent public contract | Route aliases and query IDs; filter cascades and remembered choices; performed search versus initial background reads; pending/approved accounts; editable profiles; stale asynchronous responses; recovery and bounded storage | A correct-looking form can submit the wrong fields or let an older response overwrite newer navigation. An empty result is different from a search that has never happened. |
| Renderer contract | Required fields, actions, local disclosures, readonly captured profile, formatting school objects, password fields, and the shared diagnostic controls | This catches missing buttons and accidental object-to-text rendering before the browser runs. It does not establish visual fidelity. |
| Community behavior and independent community contract | Threads, replies, ordering, search, votes, author permissions, reports, hide/restore, persistence; corrupt/duplicate/oversized restored data; writes to hidden topics | A forum must remain consistent after reload and malformed data. A visual list alone does not demonstrate working participation or moderation. Local roles are an authored simulation. |
| Actual browser journeys | Real typing, clicks and keyboard actions through registration, Terms, approval, typed login, profile editing/public display, directory, Contact, wishlist/share handoffs, forum and diagnostics | I do not inject login state to prove the teacher flow. Browser checks caught blocked pointer targets, hidden controls, lost spaces and disclosure/focus problems that pure function checks missed. |
| Inspector continuity | The original DevTools mount, navigation and panel remain the same connected nodes across actual navigation; refresh and close still work | Removing a duplicated footer must preserve the working inspection tools. Merely finding an element with the same ID would miss destroying and recreating it. |
| Visual comparison | Captured source and local pages at matching desktop/mobile viewports, plus expanded Menu and Terms; fonts, genuine assets, spacing, colors, card structure and copy | Successful loading and equal asset hashes missed large layout differences. Pairs keep native dimensions rather than resizing screenshots to look similar. Intentional local improvements are recorded separately. |
| Responsive and runtime boundaries | Standalone and embedded views; overflow, missing images, console errors, external requests, reduced motion and keyboard focus | A page can work directly and fail inside PageRouter. Local account/contact/payment handoffs must remain unsent. |
| Native build and output verification | The pinned Bazel/Node build, existing regressions, import relocation and closure, compiled artifact manifest and hashes | Source imports can work locally but break after packaging. The delivered artifact, including its generated metadata, is the thing that needs verification. |
| Publication binding | Rehash current native inputs and recipe independently, compare committed Git blobs to the receipt, push only main and verify remote readback | A historical passing build cannot validate newer edits. The independent checker demonstrably rejects the retained earlier receipt after source changes. |
| Deployment readback | Check the main-triggered Pages workflow and fetch deployed entry/modules/styles to compare them with the verified native artifact | A successful push does not prove the new UI reached the public site. Deployment is reported separately until read back. |

I retain failed receipts and corrected test assumptions. A test selector that incorrectly assumes a CSS class is repaired as a test; a real blocked Close button is repaired as product behavior. Their evidence stays separate.

The acceptance matrix records each original gap and its current proof. Final artifact and deployment identities are written only after their checks complete.
