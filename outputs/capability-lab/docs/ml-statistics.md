# Linear regression and watch calibration data

This module provides a small linear-regression trainer and prediction function, plus a synthetic watch-timing dataset built by advancing the watch transport. The watch observations are generated teaching data, not physical measurements.

## Linear regression

`fitLinearRegression({features, targets, fitIntercept = true})` fits a line or plane through numeric rows. A *feature* is an input value the model may use; a *target* is the value it tries to predict. With an intercept, the model is `prediction = intercept + Σ(featureᵢ × coefficientᵢ)`. Without one, the intercept is fixed at zero.

The fit uses the repository's QR-based least-squares solver. In plain terms, it chooses coefficients that make the squared prediction errors as small as possible without forming the numerically fragile normal-equation product. It accepts an overdetermined fit (more rows than coefficients), but rejects fewer rows than fitted values and rank-deficient inputs, where columns do not provide enough independent information to identify a unique fit.

The returned `model` contains only reusable parameters and shape metadata: `kind`, `version`, `coefficients`, `intercept`, `featureCount`, `sampleCount`, `fitIntercept`, and `solver`. It does not retain targets. `diagnostics` includes fitted values, residuals, residual norm, and matrix rank. A *residual* is `target - prediction`; it shows the error on a training row, not a promise about future data. `predictLinearRegression({model, features})` accepts only the retained model and new feature rows.

Inputs are finite JSON numbers. Work is bounded to 10,000 rows, 64 features, and 100,000 design or prediction matrix cells. Regression is an association model: a fitted coefficient does not establish that a feature causes the target.

## Synthetic watch calibration

`buildWatchCalibrationDataset({conditions, earlySeconds = 5, horizonSeconds = 30, seed = 1})` creates one independent transport run for each condition. Each condition has `{conditionId, mechanicalHz}`; `mechanicalHz` is a positive integer or an exact `{numerator, denominator}` rational no greater than 8 Hz. Decimal rates should be supplied exactly, for example `{numerator: 37, denominator: 10}`. Explicit datasets need 4–64 unique conditions. The early and horizon times are positive integer seconds, the horizon must be later than the early observation, and both are capped at one day.

If `conditions` is omitted, the seeded xorshift32 generator and Fisher–Yates shuffle select seven unique rates from the fixed 3.70–4.30 Hz grid in 0.05 Hz increments. Seed zero maps to a documented nonzero PRNG state. The recipe seed and early/horizon times are recorded in provenance. Default condition IDs hash the normalized exact rate, so the same simulated rate keeps the same group ID across seeds. Each run ID includes the seed and time recipe, so separate simulations remain separate runs. For explicit conditions, callers should reuse a `conditionId` for the same experimental condition when combining datasets; a new arbitrary ID for an existing rate defeats cross-dataset grouping.

The only selectable feature is `earlyObservedMechanicalHz`. Its value is the exact retained mechanical cycle phase divided by twice the powered operating time. For example, 3.75 Hz over 5 seconds gives 75/2 cycles, even though the completed-beat counter shows 37; `(75/2) / (2 × 5)` gives 3.75 Hz. `observations.earlyMechanicalCycles` stores that phase as a rational, and `earlyOperatingTime` stores the powered time used. `earlyObservationWindowSeconds`, `readoutKind: 'synthetic-teaching-phase-observation'`, and `formula: 'earlyMechanicalCycles/(2*earlyOperatingTime)'` make the derivation explicit. The phase is an observable of this teaching simulator, not a physical watch measurement. The target `horizonClockErrorSeconds` is the retained mechanical display time at the horizon minus the logical horizon seconds. Each row also keeps `earlyMechanicalBeats`, `earlyDisplayTime`, `horizonMechanicalBeats`, `horizonOperatingTime`, and `horizonDisplayTime` in `observations`, allowing the feature and target to be checked from the watch state. Configured rates are stored in dataset provenance and never copied into feature vectors. Future horizon observations are also metadata, never features.

Use `splitByGroup` on whole `runId` and `conditionId` groups before training or evaluation. A *holdout* is a group of records set aside from fitting to check how the model behaves on unseen runs or conditions. Repeated records from the same run or condition must not cross that boundary. A grouped split on a small synthetic dataset is only a teaching demonstration, not evidence of generalization to physical watches.

`predictAnalyticalWatchBaseline({features, nominalMechanicalHz, horizonSeconds})` computes the ideal continuous drift `(observedRate / nominalRate - 1) × horizon`. It uses only the early observed rate, nominal design rate, and horizon, never targets. The actual watch target follows discrete beat/display boundaries, so it can trail ideal drift by less than one nominal beat: with the 4 Hz design rate, one beat is `1/8` second. A baseline that performs as well as or better than regression is a useful result: the synthetic data follows the rate formula by construction.

In the retained seven-rate grid, a grouped holdout replay (seed 113, split seed 8) measured regression MAE about `1.17 × 10⁻¹⁵` seconds, analytical-baseline MAE about `6.66 × 10⁻¹⁶` seconds, and training-mean MAE `1.125` seconds. The analytical formula won by floating-point rounding, as expected for data generated directly from that rate relation. This is an arithmetic check over noiseless integer-horizon simulations; it does not establish physical accuracy or generalization to real watches.

## Shared data tools

The companion data module accepts records with `runId`, `conditionId`, a numeric `features` vector, and (for supervised tasks) `target`. `splitByGroup({records, groupBy = 'conditionId', testFraction = 0.2, seed = 0})` holds out whole connected groups: records sharing a run, condition, or selected grouping value stay together. A *holdout* is data reserved to check the fitted model after training; keeping groups intact prevents repeated samples from the same run or condition from appearing on both sides.

`fitStandardizer({features})` stores each training column's mean and population standard deviation. Standardization means subtracting the training mean and dividing by that stored scale. A constant training column uses scale 1 and is marked constant; `transformStandardizer({model, features})` reuses the fitted values without learning from new rows. Fit the standardizer on training rows only, then apply the same model to holdout rows.

`fitMeanBaseline({targets})` stores the training-target mean, and `predictMeanBaseline({model, count})` repeats it. This provides a simple benchmark that does not use input features. `regressionMetrics({actual, predicted})` reports count, mean absolute error (MAE), mean squared error (MSE), root mean squared error (RMSE), and R². MAE is average absolute miss; MSE averages squared misses; RMSE expresses that squared measure back in the target's units. R² compares model error with variation around the actual mean, and is `null` when all actual values are constant.

`classificationMetrics({actual, predicted})` reports a confusion matrix and accuracy plus macro-averaged precision, recall, and F1. A confusion matrix counts actual labels by row and predicted labels by column. Macro scores compute a score for each integer class, then average classes equally; a missing denominator gives that class a zero score. `selectFeatures({dataset, featureNames})` maps explicitly named input columns to positions and rejects known direct leakage names such as targets, identifiers, future observations, and configured faults. It cannot identify every disguised feature with misleading semantics, so the declared feature meaning still needs review.

These functions are dependency-free browser-safe ES modules. The regression descriptors compose through actual `linalg.leastSquares` and `linalg.dot` calls so their calculation trace exposes the numerical work.
